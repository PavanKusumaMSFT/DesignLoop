System Architecture

How Design Loop
thinks and runs.

A three-tier agent system where every stage of the design process is powered by tools that can be invoked at any granularity — full lifecycle, a single stage, or a single tool directly.

Every tool must produce specific, evidenced, task-grounded output — or it re-runs once with surgical precision before the user is involved.

No slop. No generic output. Every artifact is verified before it leaves a tool.

Atomic Unit

Three files. One folder. One tool.

Every capability in the system is a tool — self-describing, self-sufficient, and independently invocable.

tool.json
Contribution Contract
Declares the tool's identity — which stage it belongs to, what inputs it needs, what outputs it produces, and which tools must run before it.
SKILL.md
Execution Instructions
How to run the tool. Self-sufficient — works standalone without any other context. Contains the full prompt and step-by-step instructions for the sub-agent.
VERIFY.md
Quality Rubric
Dimensions, weights, and thresholds for scoring output. The verifier uses this to decide ACCEPT or RE-RUN — with tool-specific failure instructions baked in.
// tool.json — example: competitive-analysis
{
  "id":          "competitive-analysis",
  "name":        "Competitive Analysis",
  "description": "Analyse competing products to identify gaps and opportunities",
  "stages":      ["discover"],
  "agent":       "competitive-analysis",
  "inputs": [
    { "type": "task-description", "required": true },
    { "type": "artifact", "from": "research-brief", "required": false }
  ],
  "outputs":      ["research/competitive-analysis.md"],
  "dependencies": [],
  "required":     false
}
Field What it declares
`stages`Which stage(s) this tool belongs to — tools can span multiple stages
`agent`The sub-agent that runs this tool
`inputs`What it needs — from user or from another tool's output artifact
`outputs`Artifacts it produces, written to specific file paths
`dependencies`Tool IDs that must complete before this one runs
`required`Whether this tool is mandatory for the stage to be considered complete
Quality Gate

Every output is verified before it leaves.

The verifier is an autonomous decision-maker — it scores the output and decides ACCEPT or RE-RUN. Only one re-run is allowed.

Stage Agent

Coordinator, not worker.

The stage agent reads context and selects tools intelligently — it doesn't always run everything. It skips what's already done and parallelises what it can.

⟳
Decision · Skip
Artifact exists and looks complete
The stage agent checks what's already on disk. If a tool's output artifact exists and appears complete, the tool is skipped — no redundant work.
▶
Decision · Run
Output is missing or stale
If the artifact is absent or its dependencies have changed since it was last run, the stage agent queues the tool for execution and tracks its completion.
⇉
Decision · Parallel
No dependency between tools
Parallelism is inferred from dependencies in tool.json. If two tools declare no shared dependency, the stage agent runs them concurrently — no explicit parallel flag needed.

Open-Source Model

Contributing a tool is adding a folder.

The tool registry is directory-based. No central file to edit. No merge conflicts. The system discovers new tools automatically.

1

Create a folder under .github/skills/

Name it after your tool. This is the complete unit of contribution — self-contained, self-describing.

2

Add tool.json

Fill out the contribution contract — stages, inputs, outputs, dependencies, agent name.

3

Write SKILL.md

Write precise, standalone execution instructions. Must be specific enough to pass on first try — the re-run is a safety net, not a crutch.

4

Write VERIFY.md

Define quality dimensions, weights, and thresholds. Include pre-defined failure instructions — you know your tool's failure modes best.

# That's it. The system discovers it automatically.

.github/skills/
  └── my-new-tool/
        ├── tool.json   ← contribution contract
        ├── SKILL.md    ← how to run me
        └── VERIFY.md   ← how to judge my output

# New stages work the same way:

.github/skills/
  └── my-new-stage/
        └── STAGE.md    ← stage playbook

Mirrors how successful open-source ecosystems work — VS Code extensions, GitHub Actions, npm packages. Each unit is self-describing.

Design Decisions

Eight choices that define the system.

Each architectural decision was made to balance open-source contribution ease, system reliability, and user control.

Tool Registry
Directory-based discovery
Open-source friendly — no central file, no merge conflicts. Scans .github/skills/ and builds the registry dynamically.
Agent Per Tool
One sub-agent per tool, always
Uniform architecture enables independent invocation, parallelism, and independent upgrades regardless of tool complexity.
Stage Agent Role
Coordinator, not worker
Context-aware selection means it skips what's already done, parallelises what's independent, and runs only what's needed.
Dependencies
Dual declaration — STAGE.md + SKILL.md
Supports both invocation paths equally — running a full stage reads STAGE.md, running a single tool reads its own SKILL.md.
Verify Re-runs
Strictly 1 re-run allowed
SKILL.md must be precise enough to get it right first. The re-run is a safety net, not a loop — prevents runaway retries.
Failure Instructions
Pre-defined in VERIFY.md + dynamic from verifier
Contributors know their tool's failure modes best. Pre-defined instructions take priority; dynamic specifics fill in the actual numbers.
Metric Dimensions
Tool-specific, weighted per tool
Different tools have different quality signatures — a competitive analysis weights evidence heavily; a persona weights specificity.
Hard Stop Behaviour
Flag user with best output + specific failures
User stays in control. Not overwhelmed by retry noise. Receives the best output produced so far alongside the exact failure reasons.
